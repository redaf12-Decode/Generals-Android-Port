# Development Diary - November 2026

---

## 2026-11-04: The financial-support system is gone

Owner's request: no card, message, window or link asking for financial support should reach the
player anywhere in the app. The obvious part was one call -- `buildSupportSection(page)` on the
Help page -- but the support UI was not self-contained in `SetupActivity`: its text came from
`update/support.json`, published on the `updates` branch and rendered at runtime by `SupportLinks`,
with `UpdateManager` downloading and digest-checking it against the signed manifest. Removing only
the Help-page call would have left the popup (`maybeShowSupportPopup`, shown once per published id)
and the download path live, so the whole chain went together.

Gone, in `android/`:

- `SetupActivity`: the `buildSupportSection` call, and the methods `buildSupportSection`,
  `renderSupportBlocks`, `maybeShowSupportPopup`, `copySupportAddress` and `openSupportLink`; both
  `maybeShowSupportPopup()` call sites (in `onCreate` and in the update-check callback, where
  `r.supportUpdated` also forced a Help-page refresh); the `PREF_SUPPORT_POPUP_SEEN` key.
- `UpdateManager`: `applySupport()`, the `supportUpdated` field and its assignment, and the javadoc
  bullet. A manifest that still carries a `"support"` entry is now simply ignored -- the signed
  manifest on the branch needs no change for the app to stop showing anything.
- `SupportLinks.java` (370 lines) deleted; `SetupActivity` was its only consumer.
- `setup_support_popup_later` removed from all 13 locale `strings.xml`.
- `ic_gzh_heart.xml` deleted. `ic_gzh_copy` stays -- `NetworkDiagnosticsActivity` and other rows use
  it, so it was never support-specific.

And outside `android/`, so the source stops carrying the payload at all:

- `update/support.json` deleted, and with it the `--support` option and the `support/<digest>.json`
  publishing block in `scripts/update/publish-update.py` (the manifest no longer gets a `support`
  key). Verified by running the script: it produces `manifest.json` and `datapack-manifest.json`
  and nothing else.
- `docs/HOWTO/PUBLISH_UPDATE.md`: the "Support card" bullet and the "Monthly heroes" section.
- `docs/port/ANDROID_PORT.md`: the support-card bullet and "support the project" in the Help-page
  description.

633 lines removed from the app in one commit, and none added. Checked by compiling the whole Java
shell with `javac` against `android-35.jar` plus the material/core/appcompat/cardview jars -- zero
errors, and the pre-change tree compiles clean the same way, so the removal is not hiding a
regression. The two deleted resources are exactly the two that disappear from the generated `R`.

**Still to do, and it needs the owner:** the `updates` branch already published carries a `support`
entry naming a `support/<digest>.json`. A launcher built before this change will keep showing the
card until the next settings publish, and only a publish can withdraw it -- the code change alone
cannot. Publish settings once (`publish-update.py --out ...`, then `push-updates-branch.sh`, then
**Actions → Sign update**) to drop the entry from the live manifest.

The historical October diary and the `v1.4.0`/`v1.4.1`/`v1.4.2` release notes described the support
card as it was when those shipped. The owner then asked for every trace of the appeal to go, not
just the code path, so those too were stripped -- see the entry below.

## 2026-11-04: The in-app updater is gone from the launcher

The owner asked for the app-update feature to be removed from the interface, and then chose the
fuller of the two options offered: drop the **Updates** card *and* stop the silent check behind
it, rather than keep updating the engine with no UI. The consequence was stated before the work
started and accepted: **an engine update now needs a new APK**.

The card was the last card on **Home** (`SetupActivity.buildHomeSection`), and it was the only
caller of `UpdateManager.check(ctx, true)`. Removed with it:

- `buildUpdatesSection`, `refreshUpdatesStatus` and `runUpdateCheck` in `SetupActivity`, the four
  fields they used (`updatesStatusView`, `updatesOpenOnlineButton`, `updateCheckRunning`,
  `sAutoUpdateCheckedThisProcess`), the `refreshUpdatesStatus()` calls in `onResume` and
  `buildUi`, and the once-per-process automatic check. Nothing else called any of them.
- 19 string resources, from all 13 locale `strings.xml` (247 lines): the card title and help, the
  status line and its engine/when parts, the button, the switch and its description, and every
  toast the check could raise. `setup_updates_datapack_installed` was **kept** -- the
  GeneralsOnline screen's data card uses it. Each locale still has the same 468 string names as
  `values/`.
- The stale prose: `README.md`'s feature row now says the engine update was removed and needs a new
  APK; `docs/port/ANDROID_PORT.md` §4a and `docs/HOWTO/PUBLISH_UPDATE.md` describe settings-only
  checks; comments in `UpdateManager` and `GeneralsOnlineActivity` no longer point at a card that
  is not there.

One trap found on the way. The removed **"Check automatically"** switch wrote the `auto_check`
preference, and it was the *only* writer -- but `GeneralsOnlineActivity.maybeAutoCheckDataPacks`
still gated the community data patch on it. A player who had ever turned it off would have kept
the patch frozen with no UI left to re-enable it. That gate is gone: the data card always checks
the signed settings (a few lines, and `pc_crossplay`/the servers must reach everyone online) and
still downloads the patch only on an unmetered network.

Left in place on purpose: `UpdateManager`'s engine-download path, the `engine` entry in the
manifest and the engine publishing steps in `publish-update.py`. The card was removed, not the
format, so restoring the card restores the old behaviour. `UpdateManager.check`'s `withEngine`
parameter is now always `false`, and the `isAutoCheckEnabled`/`setAutoCheckEnabled` accessors
have no caller left -- both are kept, with the javadoc and a comment saying so, so a restore is
one file, not an archaeology exercise.

Verified by compiling the whole Java shell with `javac` against `android-35.jar` plus the
material/core/appcompat/cardview jars -- zero errors, 62 classes, and the pre-change tree
compiles the same way, so the removal hides no regression. Every `R.string.*` the removed code
used was checked to be unused elsewhere before its resource line was deleted.
