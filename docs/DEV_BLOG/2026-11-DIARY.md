## 2026-11-05: 40 buttons, a Hide toolbox that really hides, and the empty editor

Three more requests on top of the morning's editor work, all in the same feature. Each one had a
cause worth writing down.

### 40 buttons

`TouchControlConfig.MAX_BUTTONS` was 20 -- the reference's ceiling. Raised to 40. The important
part is that the limit is enforced in **four** places and only one of them is the constant:
`TouchLayoutEditor.addButton()` refuses at the maximum, `readButtons()` stops reading at it, and
`fromJsonString()` refuses a document that carries more than it. They all read the one constant, so
raising it raised all four. `TouchControlConfig.SCHEMA` went 3 -> 4 so a document written with 40
buttons is not read as a v3 one; older documents are still accepted (v1..v4), and because the
loader stops at `MAX_BUTTONS` and never trims below it, an existing layout of 20 loads with all 20.
A new test walks to 39, adds the 40th, asserts the 41st is refused, and reloads to check all 40
survive with their positions.

### Hide toolbox did not hide the toolbox

The row said "Hide toolbox" and only closed the panel -- the icon stayed, so the toolbox was never
actually hidden. The fix separates the states instead of overloading one flag:

* `TouchControlConfig.enabled` -- the game buttons (untouched by hiding).
* `ToolboxConfig.iconVisible` -- the floating icon (new; false after hiding).
* `ToolboxConfig.panelOpen` -- the panel.
* the editor's `editing` flag -- the edit session.

`hideToolbox()` now writes `iconVisible = false` and `panelOpen = false` and **never touches
`TouchControlConfig`**, so every game button stays visible, keeps its key and the layer stays on.
Both `onDraw` and `onTouchEvent` consult `iconVisible`, so the icon is gone and its tap/drag area
with it -- no invisible clickable box left behind. `iconVisible` defaults to true and is stored per
game, so an existing install keeps its icon where it was; the value is independent of `enabled`, so
"the player hid it" and "the toolbox was never wanted" stay distinguishable.

The way back is a new **Show toolbox** action in the launcher's touch-controls card, which sets
`iconVisible = true` (and `enabled = true`, so it is not a silent no-op if the switch was off). The
stored position is preserved, so the icon returns where the player last dragged it.

### The editor looked empty because every button was in one pixel

The report was "the editor opens but the buttons do not appear". Reproduced deterministically: the
overlay is a full-screen view that is `GONE` whenever the button layer is switched off, and a
`GONE` view is never measured, so `getWidth()`/`getHeight()` are 0. `applyViewport()` and
`rebuildGeometry()` fell back to a **1x1** viewport (`getWidth() > 0 ? getWidth() : 1`), which makes
every stored fraction resolve to the same pixel -- all ten buttons drawn inside the top-left pixel.
The editing surface was not blank; it was ten buttons on top of each other at (0,0). A temporary
harness rendered the real view and counted the button's own fill pixels: 0 with the 1x1 fallback,
2581 once the viewport was the real window. The fix is `viewportWidth()`/`viewportHeight()`, which
fall back to the display metrics instead of 1, so the editor draws the real layout before the first
layout pass. `theInGameEditorDrawsTheExistingButtons` now drives the real toolbox Edit row and
counts pixels, so the regression cannot come back silently.

### Placement is the whole screen

The editor clamped every button inside a safe area: `setCenterPixels()` kept the whole box clear of
the system insets and inside `MIN_X/MAX_X/MIN_Y/MAX_Y`, `placeNewButton()` searched a ring that
avoided the insets and the toolbar strip, and `resizeTo()` clamped the centre again. That is why a
button could not reach a corner or sit over the HUD. The `Viewport` insets are gone; `MIN_X/MAX_X/
MIN_Y/MAX_Y` are now 0..1 (the whole screen, not 0.02..0.98), and `setCenterPixels()` only rejects a
non-finite or out-of-range value -- it no longer clamps the box. `placeNewButton()` keeps a small
margin only for the ONE button being created, so a new button is not dropped flush under the
toolbar; a button the player then drags is never re-homed. Overlap, corners, the HUD and a button
hanging half past the edge are all allowed, and the centre stays on screen so it is always
recoverable through the editor. New tests pin the corners exactly, two buttons on one point, a box
that reaches outside, and a corner position surviving a save/reload.

**Verification.** 100 JVM tests, all green (7 suites: routing 12, appearance 25, config 12, editor
24, shapes 9, key catalog 7, key presser 11). `gradle :app:testDebugUnitTest` reaches
`BUILD SUCCESSFUL` on JDK 21 with the SDK under `/workspace/.buildtools`. All 13 locale files carry
the new strings, name-for-name against `values/`. As before this is a Java/JVM build, not a
device-verified APK.

## 2026-11-05: the touch editor gets its missing "+", a real toolbox icon, and its own colours

The in-game button editor had a toolbar with ten cells and no way to add a button; the floating
toolbox could do everything except that one thing; and the icon was a hand-drawn X over a
wrench-shape, which reads as "close", not "tools". Three separate requests, one session.

### Why Add was missing

It was never wired, not broken. `HotkeyOverlayView` had `TOOL_COUNT = 8` with no `TOOL_ADD`, and
`runTool()` had no case for one -- the *model* already had `TouchLayoutEditor.addButton()`, and the
launcher's full-screen editor already called it. So the fix is small: a tenth cell that calls the
same model method, plus a row in the toolbox panel that calls it too. All three entry points
(launcher footer, editor toolbar, toolbox) now run one implementation, so the maximum-button rule
and the placement rule cannot disagree between them.

Two things came out of doing it properly rather than just adding a cell:

* **A new button used to land at (0.5, 0.6)**, which is exactly where the toolbar sits on a phone
  in landscape. It is now placed by a bounded ring search from the centre outwards: clear of the
  toolbar (the editor is told the toolbar's height), inside the insets, and -- when there is room --
  not on top of a button that is live in the match.
* **The toolbar label for the shape button can be a word** ("Pentagon"), and ten cells on a phone
  are narrow, so every toolbar and menu label is now shrunk until it fits its own cell.

### The accent-colour bug, and why it looked like a border bug

`TouchEditorRenderer` drew a selected button *by repainting the button*: `borderPaint.setColor(
accentColor)` and a stroke 3dp wide, over the button's own outline. Entering the editor therefore
recoloured the selected button in the launcher's accent, and it read as "my border colour was
overwritten". The correction is not to hide the selection but to move it: the button is now always
drawn with `fillColor`/`borderColor`/`textColor` exactly as the match draws it, and selection is an
accent dashed frame drawn *outside* its box, plus the resize handle and the position badge. A test
samples every pixel inside a selected button and asserts the accent appears nowhere in it.

### The icon

The supplied Flaticon asset (`control_6841795`) is "Control" by **Creatype** -- the page's author
line, not Freepik, which is what the URL pattern suggests at a glance. It is traced to a
VectorDrawable (`res/drawable/ic_gzh_toolbox.xml`, 24dp, `viewportWidth 512`) so it stays sharp at
every density, and rasterised once at construction into a bitmap the toolbox draws scaled and
centred. Nothing is fetched at runtime. Checked against the source PNG's alpha: IoU 0.972.

Attribution is the Flaticon Free License's condition, so it ships in three places: the drawable's
header, a new `CREDITS.md`, and -- because the licence wants the credit *in the app* -- a caption
in the launcher's About card, in all 13 locales.

### What else landed

Hide Toolbox (a row that closes the panel and keeps the icon; the state is stored per game,
separate from the buttons' own enabled flag, so hiding the panel never disables a control); a shape
menu (six shapes, then four polygon types) whose cells drive the model and whose labels are
localised; and `unitTests.includeAndroidResources = true` in `build.gradle`, without which the
Robolectric tests that drive the real toolbox rows fail on `Resources$NotFoundException`.

### Evidence

`./gradlew :app:assembleDebug` green; 83 unit tests across six classes, 0 failures. The new tests
drive the real views through real `MotionEvent`s -- a tap on the toolbar's "+" cell, a tap on the
shape menu, a tap on the toolbox's Add row -- and assert the model changed, not that a UI element
exists. No native file was touched: `git status` shows only `android/app/**`, the strings, the
README and `CREDITS.md`.


## 2026-11-04: the single custom driver became a library

Asked to "complete the Vulkan feature" on `New-app` against the `fix-ui-Draw-18-10` reference:
import definitions into the graphics list, show each one's name and version, allow more than one,
let the active one be chosen and deleted, add a return-to-default option, wire it to the existing
SDL/libadrenotools loading, and persist the choice across restarts.

The reference branch, again, had nothing for this: a whole-block diff of its driver code against
`New-app` is identical apart from the missing `custom_driver.info` sidecar and the older
`libraryName`-only status line. What `New-app` actually had was **one** driver slot — the engine
reads `custom_driver.cfg` plus `custom_driver/`, and importing replaced the whole thing. So the
work was to build the library the request describes on top of that one slot, without touching the
slot's contract.

### The design, in one line

Every imported driver is kept in its own folder under `<internal>/drivers/`; "activating" one
copies it into the single slot the engine reads. The native side is byte-for-byte unchanged —
`TryLoadCustomVulkanDriver()` still reads `custom_driver.cfg` and `custom_driver/` and nothing
else — which is what makes the feature safe to add to a shipping loader. The storage, validation
and selection all moved into a new `DriverLibrary.java` with no `android.*` imports, next to the
existing `CustomDriverPackage`.

### The invariants the requirements asked for, and how each is held

- **GLES is always the default on a fresh install.** Nothing here is read unless
  `render_backend.cfg` says `vulkan`; `getRenderBackendChoice()` already returns GLES when that
  file is absent, and that code was not touched.
- **An existing user's default is never changed.** The driver library is only consulted from the
  Vulkan-only branch of the Graphics tab. No render-backend default moved.
- **OpenGL ES / ANGLE / Vulkan all remain.** `RENDER_BACKEND_CHOICES*`, the picker and
  `moveOffVulkanOnce()` are untouched.
- **No custom driver is loaded under GLES.** Unchanged: the native hook runs only inside
  `if (useVulkan)`.
- **A failed import never replaces the active driver.** Extraction and validation happen before
  anything on disk is touched, and `importDriver()` only stores a package that already passed.
  A refused package leaves both the library and the slot exactly as they were — one of the 75
  assertions exercises precisely that.

### The subtle parts

- **Atomic activation.** Making a driver active copies it into the slot after moving the previous
  slot aside; a failure restores it, so the engine is never left with a half-written driver
  directory. `reconcile()` and `cleanupInterrupted()` heal a process death between the renames,
  the same self-healing the previous commit added for imports.
- **A driver library makes "which one is active" harder than one string.** Two Turnip builds can
  ship the same soname (`libvulkan_freedreno.so`), so the active entry is matched on the soname
  *and* the slot's own `meta.json` name/version/vendor when that is readable — otherwise switching
  between such builds would leave two rows marked active. Re-importing the identical driver is
  deduplicated to one entry; a different build of the same soname stays separate.
- **Migration.** An install from before the library has its driver only in the slot, so
  `adoptActiveSlot()` copies it into the library the first time the card is built — without
  changing what is active — and it becomes listed and re-selectable instead of being stranded.

### Verification

75 assertions in a throwaway JVM harness (since deleted) against the real `DriverLibrary` and
`CustomDriverPackage`: fresh install, import, a second import, switching, persistence re-read from
disk only, a refused import leaving the active driver alone, deleting the active and a non-active
driver, reset with and without a bundled driver, reset keeping imports, `reconcile` rebuilding a
lost slot, `cleanupInterrupted` restoring a slot left as `.old`, `adoptActiveSlot`, malformed
folders skipped by `list`, and the dedupe rules above. Every one passed.

Two checks that the previous commit's CI failure taught me to run *before* pushing, since neither
is visible to a stub harness: `aapt2 compile --dir res` over the whole resource tree (all 487
strings × 13 locales compile), and a locale name-set diff (every `values-*/strings.xml` has the
same names as `values/`). `javac`'s parse API confirms `SetupActivity.java` is syntactically sound.

Not run: a Gradle build or an on-device import (no Android toolchain or device in this sandbox).
The Android-specific glue is the same three lines as before (`getContentResolver().openInputStream`
and `Build.VERSION.SDK_INT`); what is new is `File` copying and dialogs.

Ten new strings landed in all thirteen locales, and `setup_driver_help` gained a sentence in every
locale pointing at the list, the tap-to-activate row and the bin icon — the rule that a UI change
carries its help text with it.

## 2026-11-04: the custom Vulkan driver importer validates before it installs

Asked to "add or complete" the ZIP import of adrenotools Vulkan driver packages in the Graphics
settings, on the strength of a reference branch that was supposed to have it. The analysis came
first and changed the task: the feature was already there in `New-app`, and the reference branch
added nothing to it -- a whole-block diff of the driver code between the two branches is identical
apart from one unrelated `REQUEST_MODS` constant, `TryLoadCustomVulkanDriver()` in
`Core/Main/SDL3Main.cpp` is byte-identical, and all fifteen driver strings exist in all thirteen
locales. So the work became closing the gaps the task's own requirements named, rather than
porting anything.

Four real gaps, and what closed them:

- **Only `libraryName` was read from `meta.json`.** The name, vendor, driverVersion, author,
  packageVersion and minApi were all ignored, so the card could only show a file name. All of them
  are parsed now, and `minApi` is enforced against the device.
- **Nothing checked that the named `.so` was a driver.** A package could name an x86 or 32-bit
  library and install cleanly, then fail much later inside adrenotools with a bare `ENOENT`. The
  ELF header is checked now: 64-bit, little-endian, `EM_AARCH64`.
- **The install was not atomic.** `deleteRecursive(destDir)` ran *before* the rename, so a rename
  that failed left the phone with no driver at all -- and `custom_driver.cfg` still naming one.
  The current driver is now moved aside first and restored if anything fails.
- **A refusal said "Import failed: <exception text>"**, which tells a player nothing about whether
  to re-download the package or pick a different one. Every refusal now has its own sentence, in
  all thirteen languages.

The pipeline moved into a new `CustomDriverPackage.java` with no `android.*` imports, which is what
made the testing possible at all: the app has no test infrastructure, but this class runs under a
plain JVM, so the ten cases the task lists were exercised against the real code rather than
reasoned about. A throwaway harness (70 assertions, since deleted) covered a valid package, a
nested one, no `meta.json`, a missing `.so`, a corrupt zip, Zip Slip (`../../`), an absolute path,
replacing a working driver with a refused one, `minApi`, a non-ELF and a 32-bit `.so`, two
`meta.json` files, a malformed one, an empty `libraryName`, a separator in `libraryName`, atomic
config writes, cancel, restart, reset, and a process killed between the install's two renames.

Three things worth remembering:

- **The atomic swap introduced a crash window the old code could not have.** Between the two
  renames the previous driver sits in `custom_driver.old` and nothing is in `custom_driver/`. A
  process death there would have stranded the phone on its stock driver, so
  `recoverInterruptedInstall()` heals it -- called before every import and whenever the card is
  built. Improving a failure mode can create a new one.
- **Two strings lost their last reader** (`..._import_no_finalize`, `..._config_failed`) and were
  removed from all thirteen locales in the same commit, per the rule that every locale keeps the
  same set of names. Both files were then re-parsed and the sets compared.
- **Phase 4 held by construction, not by care.** `SDL3Main.cpp`, `adrenotools.cmake`,
  `build.gradle` and `fetch-turnip.sh` are untouched (`git diff --quiet` on each); the native side
  reads exactly the `custom_driver.cfg` + `custom_driver/` it read before. The new
  `custom_driver.info` sidecar is launcher-only, and a missing one falls back to the old wording.

Not run: a Gradle build or an on-device import (no Android toolchain or device in this sandbox).
The Java was compiled and exercised on a JVM against `org.json`, and both edited files parse; what
remains unverified is the Android-specific glue -- `getContentResolver().openInputStream()` and the
`Build.VERSION.SDK_INT` argument -- which is three lines and unchanged in shape from before.

## 2026-11-04: build-android.yml now builds all four engines

Owner's request: fix `build-android.yml` so it builds four engines -- `g_generals` and `z_generals`
at both 30 Hz and 60 Hz. It built exactly one before: a single `z_generals` pass with
`SAGE_HIGH_FPS_SIM` left at its OFF default, so the APK had only Zero Hour's 30 Hz engine, and no
base-game engine at all (`g_generals` was never named as a target).

The workflow now mirrors `scripts/build/android/build-dual-hz.sh`: pass 1 configures with
`-DSAGE_HIGH_FPS_SIM=ON` and builds `z_generals g_generals` plus DXVK and the four adrenotools
hooks (rate-independent, so only this pass builds them), then stashes the two 60 Hz engines as
`build/libmain60.so` / `build/libgenerals60.so`; pass 2 reconfigures with `SAGE_HIGH_FPS_SIM=OFF`
and rebuilds only the two engines, producing the 30 Hz pair. The packaging step passes both stashes
via `GX_SECOND_GAME_LIB` / `GX_SECOND_BASE_GAME_LIB`, so `package-android-zh.sh` stages all four
into `jniLibs/`. `timeout-minutes` went 120 -> 300, since a cold run is now roughly four engine
builds.

Two things were wrong in the old workflow and are fixed while here:

- The DXVK check was `strings ... | grep -q Sdl3WsiDriver`. Under `pipefail` that SIGPIPEs the
  still-writing `strings` on the first match (fails a good library), and `Sdl3WsiDriver` is a C++
  class name that is not retained as raw text in a release binary -- the string to look for is its
  runtime log prefix `SDL3 WSI:`. The local sandboxed build had already fixed both; CI had not.
- The strip step did not strip the base-game engine at all, and the stashed 60 Hz pair was copied
  out of the build tree before the strip step ran, so the APK would have carried two unstripped
  ~282 MB engines. All four are now stripped in one place.

Also extended to match the four engines: the symbol-table step emits one table per engine (any of
the four can be the one in a tombstone), the Release attaches all four, the in-APK check asserts all
four are present, and `publish-release.yml`'s release check now requires `libgenerals*.so` too.

Verified with `python3 -c "import yaml; yaml.safe_load(...)"` on both workflows and `bash -n` on
every `run:` block. Not run: the build itself (no Android toolchain in this sandbox) -- the change
is a workflow restructuring, and CI does not fire on push.

## 2026-11-04: Dead code removed, and two lifecycle leaks found while looking

Owner's request: remove the dead code and find the bugs that hurt the app's life cycle. The two
were done in that order, and the second one turned up more than the first.

### Dead code

Confirmed by static analysis of the Java shell (every candidate re-checked by hand before removal;
a hit in the manifest, in a `.wnd`/`.xml` layout, or behind a `getIdentifier` name lookup counts as
a use, and there are no XML layouts in this app -- the UI is built in code):

- `ModLibraryInfo.isManagedEntry(File, File)` -- declared, never called. `ModLibraryInfo.measure`
  is the only entry point `ModManagerActivity` uses.
- `ModManager.enabledCount(Context)` -- declared, never called; the enabled count shown in the mods
  screen is computed in `ModManagerActivity` itself.
- `UpdateManager.isAutoCheckEnabled` / `setAutoCheckEnabled` -- left behind when the Home Updates
  card went (previous entry). No caller on either side.
- `FolderPickerActivity`: `import java.util.Arrays` -- unused.
- 11 string resources in all 13 locales (468 -> 457): `setup_language_game_status_default`,
  `_override`, `_missing`, `setup_button_change_render_backend`, `setup_langpack_done`,
  `setup_langpack_not_available`, `setup_langpack_dialog_title`, `setup_toast_folder_saved_invalid`,
  `setup_toast_folder_saved_incomplete`, `online_status_signin_failed`, `online_status_unexpected`.
  Locale parity re-checked afterwards: every `values-*/strings.xml` has exactly the same names.
- `ic_launcher_setup.xml` + `ic_launcher_setup_foreground.xml` + `ic_launcher_setup_background.xml`:
  a second launcher icon referenced by nothing. The manifest declares no `activity-alias` and its
  only icon is `@mipmap/ic_launcher`, so this whole set was unreachable. (This clone is shallow, so
  which commit left it behind is not verifiable here.)

Deliberately **not** removed, and why: the `gzh_navy_*`/`gzh_day_*` colours look unreferenced but
`ThemeHelper.mapColor()` resolves them by name at runtime (`res.getIdentifier("gzh_navy_" + ...)`),
so they are live; `UpdateManager.KEY_AUTO` and `lastCheckMillis` are kept as the documented name and
reader of a stored preference, so restoring the card keeps whatever a player had chosen. The two
"Change Render Backend" dialog strings are kept on purpose too -- see the comment at
`SetupActivity.buildSimRateSection`, which says so.

### Two lifecycle bugs

Both are leaks that outlive the screen, both found by asking "who releases this, and when".

1. **The LAN `MulticastLock` was never released at exit.** `GeneralsZHActivity` had no `onDestroy`
   at all. `udp.cpp` acquires one reference per open broadcast socket and releases it when the
   socket closes, but a socket still open when the game Activity is destroyed -- or any teardown
   that never reaches `UDP::SetBroadcastReceive(false)` -- left the lock held. A held multicast lock
   keeps Wi-Fi awake for as long as the process lives. `onDestroy` now releases it, synchronised on
   the same monitor as `setLanMulticastLock()` because the native game thread may be releasing the
   last reference at the same moment.

2. **The network-diagnostics sweep outlived its Activity.** `NetworkDiagnosticsActivity` has no
   `onDestroy`; the sweep thread reported each step through `handler.post(...)` on the main Looper,
   which is not bound to the Activity. Closing the screen mid-sweep left a thread posting to a
   destroyed Activity's views (and, because the probes carry 10 s connect/read timeouts, it could
   stay alive for the whole sweep). The thread is now held in a field, interrupted in `onDestroy`
   (`NetworkDiagnostics.run()` already checks `Thread.interrupted()` between probes), pending posts
   are dropped, and the final post re-checks `isFinishing()/isDestroyed()` to cover the race.

Checked and found **correct**, so left alone: `GeneralsOnlineActivity` retires its poll loop on
`onDestroy` when really finishing and keeps the sign-in alive across a bare recreation (the
`signInGeneration` counter); `SetupActivity`'s three language-pack threads all guard their UI
callbacks with `isFinishing()`; `ModManagerActivity` and `GeneralsOnlineActivity` shut down their
executors; every `Cursor` is in try-with-resources; there are no `registerReceiver`/`bindService`
calls, no `printStackTrace`, and no static `Context`/`View`/`Activity` fields. A few one-line silent
catches were reviewed and are intentional fallbacks, each with a comment.

Verification: the Java shell compiles clean before and after (`javac`, EXIT=0, 65 classes both
ways), which is what makes "nothing that was live was removed" checkable rather than assumed.

## 2026-11-04: The in-app updater is gone from the launcher

The owner asked for the app-update feature to be removed from the interface, and then chose the
fuller of the two options offered: drop the **Updates** card *and* stop the silent check behind
it, rather than keep updating the engine with no UI. The consequence was stated before the work
started and accepted: **an engine update now needs a new APK**.

The card was the last card on **Home** (`SetupActivity.buildHomeSection`), and it was the only
caller of `UpdateManager.check(ctx, true)`. Removed with it:

- `buildUpdatesSection`, `refreshUpdatesStatus` and `runUpdateCheck` in `SetupActivity`, the four
  fields they used (`updatesStatusView`, `updatesOpenOnlineButton`, `updateCheckRunning`,
  `sAutoUpdateCheckedThisProcess`), the `refreshUpdatesStatus()` calls in `onResume` and
  `buildUi`, and the once-per-process automatic check. Nothing else called any of them.
- 19 string resources, from all 13 locale `strings.xml` (247 lines): the card title and help, the
  status line and its engine/when parts, the button, the switch and its description, and every
  toast the check could raise. `setup_updates_datapack_installed` was **kept** -- the
  GeneralsOnline screen's data card uses it. Each locale still has the same 468 string names as
  `values/`.
- The stale prose: `README.md`'s feature row now says the engine update was removed and needs a new
  APK; `docs/port/ANDROID_PORT.md` §4a and `docs/HOWTO/PUBLISH_UPDATE.md` describe settings-only
  checks; comments in `UpdateManager` and `GeneralsOnlineActivity` no longer point at a card that
  is not there.

One trap found on the way. The removed **"Check automatically"** switch wrote the `auto_check`
preference, and it was the *only* writer -- but `GeneralsOnlineActivity.maybeAutoCheckDataPacks`
still gated the community data patch on it. A player who had ever turned it off would have kept
the patch frozen with no UI left to re-enable it. That gate is gone: the data card always checks
the signed settings (a few lines, and `pc_crossplay`/the servers must reach everyone online) and

one file, not an archaeology exercise.

Verified by compiling the whole Java shell with `javac` against `android-35.jar` plus the

## 04/11/2026 — Accent colours for the launcher (all three palettes)

The launcher had three palettes (standard dark, navy+gold, day) and no way to change the colour
it highlights things with. The reference branches (`fix-ui-Draw-18-10`, `New/app`) carry an accent
system, but built on a different theming model: a `values/` + `values-night/` split with 12 accent
overlay themes. This branch has no `values-night/` and resolves its palettes at runtime through
`ThemeHelper.mapColor`, so the accents were ported *into* that model rather than alongside it.

The shape that made it small: `mapColor` now resolves a colour in three steps — the accent, then
the palette, then the standard name. An accent that does not define a role falls through to the
palette, which is what lets the two dark palettes tint only the accent roles while day mode also
recolours its surface ladder, with no per-palette role list to keep in sync.

- Eleven accents (blue, green, teal, orange, red, black, gray, gold, transparent, white, yellow)
  plus "default", which is the palette's own accent and stores nothing — the same convention as an
  unset theme mode.
- `colors_accents.xml` (dark, 9 roles) and `colors_accents_day.xml` (day, 17 roles) are generated
  by `scripts/tooling/theme/generate-accent-colors.py` from the reference's palette data.
- `themes_accents.xml` holds, per accent per palette, the activity overlay and the Material and
  plain-`AlertDialog` styles. The dialogs need their own styles because a dialog is a separate
  theme and never inherits the activity's accent.
- The picker is a row of swatch dots in Interface → Appearance, below the palette choice. Each dot
  is drawn in the palette now in force, so the choice is made against what the screen looks like.
- 15 new strings in all 13 locales (462 → 477 in `values/`; every locale identical, checked).

Two bugs the tests caught, both worth recording because reasoning had missed them:

1. **Shared cache across the two dark palettes.** They were sharing one colour cache per accent,
   but they name *different* resources for the same input colour (`gzh_primary` → `gzh_primary`
   vs `gzh_navy_primary`), so the first palette to populate the cache poisoned the other. Now one
   cache per palette per accent.
2. **Day ladder names did not match.** The generator named the ladder accents with the reference's
   suffixes (`..._container_surface`) while `mapColor` composes the name from the base role
   (`..._surface_container`). The reference is internally inconsistent here; the resources now
   follow the role, which is what the lookup can actually build.

Verified by driving the real `ThemeHelper` against the real resource names in a JVM harness:
63 assertions covering default-is-a-no-op, accent-over-palette in each of the three palettes, the
ladder fallback, a stale-cache regression, accent switching, and out-of-range clamping — all pass.
`SetupActivity` and `ThemeHelper` both parse, and every `R.*` reference in the changed files was
checked to exist.

Nothing existing was touched: OpenGL ES, ANGLE and Vulkan options, the default render backend,
`dxvk.conf`, the default/automatic driver mechanism and `libadrenotools` are all unchanged, and
the custom-Vulkan-driver import from the previous commit is intact.

### CI was red on this commit — three bugs the JVM harness could not see (04/11/2026, later)

The commit above pushed green locally and red on CI: run `41846155374` failed in the "Package APK"
step at `gradle assembleDebug`. The stub harness had exercised `ThemeHelper`'s Java logic but never
aapt2, so it was blind to two of the three faults; the third was a plain missing import that only
surfaced once the earlier ones stopped the build. Reproducing locally meant installing a real
toolchain (Android cmdline-tools + `platforms;android-35` + `build-tools;35.0.0` + Gradle 8.9 +
JDK 21) and staging SDL3 3.4.2's Java glue the way `package-android-zh.sh` does — `java-sdl/` is
gitignored, so `GeneralsZHActivity` cannot compile without it and every error in that file is a
harness artefact, not a defect.

1. **Unescaped apostrophes in `values-ko/strings.xml`.** `setup_toast_driver_import_missing_lib`
   and `..._bad_lib` wrapped `%1$s` in raw `'`. aapt2 rejects that ("unescaped apostrophe"),
   while the base `values/strings.xml` escapes them as `\'`. Fixed to match. Worth remembering:
   *any* locale file, not just the base one, must escape apostrophes — a per-locale review missed
   it because the base file looked right.
2. **`ACCENT_ITEMS` named roles that are never generated.** The overlay items asked for
   `container`, `on_container` and `ripple`, but `mapColor` composes a colour's name from the
   *base* colour's role, so the resources are `primary_container`, `on_primary_container` and
   `ripple_primary`. `themes_accents.xml` therefore referenced 33 colours that did not exist.
   This is the same class of mistake as bug 2 in the entry above, one layer out: the reference's
   spelling leaking into a name the lookup builds itself.
3. **`SetupActivity` used `ViewGroup` without importing it.** The accent picker's grid needs
   `android.view.ViewGroup`; every other file in the package that uses it already imports it.
   CI never got far enough to report this — it died in resource merging first.

The generator now validates its own output before writing anything: `validate()` collects every
`@color`/`@style`/`@drawable` the generated themes reference and fails the run if any of them is
undefined, listing the offenders. Proved both ways — reverting the role fix makes it exit 1 with
the 66 missing colours and leaves all three committed files byte-identical; the correct run is
idempotent. That turns a ~15-minute APK build failure into a one-second local one.

Verified end-to-end this time: a clean `gradle assembleDebug` (build dir removed) reaches
`BUILD SUCCESSFUL`, producing a 13.1 MB `app-debug.apk` whose badging is
`com.generalsx.zerohour` 1.2.8 (code 10208), minSdk 28, target/compile 35, carrying 387
`gzh_accent*` resources. Also confirmed with the real aapt2 that all 13 locale files compile and
that no locale has a stray unescaped apostrophe left.

## 05/11/2026 — The on-screen button editor, on `New-app`

`New-app` had the native SDL3 touch layer and nothing on top of it: no on-screen buttons, no
editor, no toolbox, and not one touch string in `values/`. The reference branch
`fix-ui-Draw-18-10` has that feature, so this is a port of it with the three things it lacks added
-- smooth finger dragging, the shapes, and the extended key mapping -- plus the safety it was
missing. Stage 1 was read-only; the audit is in
`docs/WORKDIR/reports/TOUCH_EDITOR_AUDIT_20261105.md`.

**The one rule everything else follows.** The overlay is a view above SDL's surface and it only
ever decides one thing: does this gesture reach the game or not. `onTouchEvent` returns `false`
for any touch that does not start on a configured, enabled button, so SDL receives the whole
gesture and the engine's own `handleTouchEvent` / `TouchInput` path runs untouched. Nothing in
`Core/**` or the native touch code changed. The editor is the one exception, and it takes
everything, because in the editor the battlefield is not being commanded.

**The key injection path is a table lookup, and that decided the design.** `TranslateKeycode` in
SDL 3.4.2's `SDL_androidkeyboard.c` maps an Android keycode to a scancode with no modifier state
involved, and the engine then latches modifiers itself in `Keyboard.cpp` (`m_modifiers |=
KEY_STATE_LCONTROL`, folded into that frame's events). So a button presses the modifier, then the
key, and the engine composes Ctrl+A on its own; the modifier is stored separately from the primary
key, which is also what lets the editor change a key without losing the player's Ctrl.

Two engine behaviours the feature has to be honest about. Alt+Tab is swallowed on purpose
(`Keyboard.cpp` marks the Tab `STATUS_USED` while Alt is down), so the editor warns when a player
builds that combination rather than pretending it will work. And a button can only ever be one of
the game's own shortcuts, because a button is a key.

**Modifiers are reference-counted, and that is the whole reason the key machine is its own
class.** Two buttons can both carry Ctrl; releasing one must not release Ctrl while the other
still holds it. `TouchKeyPresser` counts holders per key, presses modifiers before the key and
releases them after it in reverse order, and `releaseAll()` balances every outstanding down --
called on pause, on window-focus loss and on destroy, because a `Hold` interrupted by the
notification shade would otherwise hold a game binding for the rest of the process.

**Shapes are hit-tested analytically, not by bounding box.** `TouchButtonShape.contains` answers
point-in-shape for rectangle, rounded rectangle, square, circle, oval and four polygons, so the
corner of a circle's box is battlefield, not button. A bounding-box hit test would have stolen
four corner taps per circular button from the game. Square and circle take the shorter side; the
corner radius is clamped to half the shorter side.

**Dragging is absolute, not incremental.** The editor stores the grab offset and every move sets
the centre from the *current* finger position, so 500 move events leave the button exactly where
the finger is instead of accumulating rounding error. Resize anchors the opposite corner and
re-derives the size from the clamped centre, so a resize cannot walk the button across the screen.
A drag past the edge clamps to the model's limits and the button is still hit-testable afterwards.

**One edit session, two hosts.** `TouchLayoutEditor` is the model both editors drive: the in-game
mode of `HotkeyOverlayView` and the launcher's `TouchControlsActivity`. `TouchEditorRenderer`
draws the buttons in both, so a button looks the same in each and there is one place that knows how
an editable button is drawn. Each host keeps its own toolbar, because the two toolbars genuinely
differ. `TouchControlConfig` is the single store both read, so a layout saved in the launcher is in
the match on the next launch and can also be opened mid-match. It is versioned JSON with
migration: a v1 document from the reference loads unchanged, values outside the model's bounds are
clamped, a key the picker refuses drops the entry rather than injecting it later, and a document
with no usable button is refused whole instead of half-applied.

**The reference's `prepareForLaunch` is not inherited.** It deletes `Window\GroupPanel.wnd`, and on
this branch that file is the army drawer, anchored to the command bar by `GXUiScale.cpp`. Copying
it would have deleted a feature this branch has and the reference does not. The editor's guide
strip is drawn over the full window instead of assuming the bottom of the screen is free.

**Verification.** 91 JVM tests, all green: shape geometry, the config model and its migration, the
edit session's arithmetic, the key state machine, and the touch routing (the test that guards the
central promise -- empty space falls through, a button is consumed, the editor consumes
everything). The routing test runs the real view and the real hit test and replaces only the key
sink, which is native. `gradle assembleDebug` plus the test suite reach `BUILD SUCCESSFUL` with
JDK 21, SDK 35 and the SDL3 3.4.2 Java glue staged the way `package-android-zh.sh` does. The
native `.so` libraries are not built in this environment, so this is a Java/APK build, not a
device-verified APK. `aapt2 dump resources` on the built APK confirms `drawable/ic_gzh_toolbox`
is packaged as a compiled VectorDrawable, and every one of the 13 locale files carries the new
strings, verified name-for-name against `values/`.

Two build errors worth remembering. Robolectric's default SDK for this AGP version predates
`Resources.getColor(int, Theme)`, so `ThemeHelper` threw `NoSuchMethodError` in every test that
touched the overlay; `src/test/resources/robolectric.properties` with `sdk=34` fixes it. And
`MaterialSwitch` / `MaterialAlertDialogBuilder` are used fully qualified in `SetupActivity` because
that file imports the Material widgets it uses one by one.

name-for-name against `values/`.
